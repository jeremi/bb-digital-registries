## Narrative behaviour not bound by DRS-1 through DRS-37

This table records explicit behaviour in chapters 4, 7, 8, and 9 that the 37 numbered functional requirements do not fully bind.
The migration binds applicable source-only obligations in [Operate Registry Services](../requirements/operate-registry-services.md) and [Represent Registry Data](../requirements/represent-registry-data.md).
Their exact source-to-requirement bindings, retained prerequisites, and retained conflicts are recorded in [`requirement-migration.yml`](requirement-migration.yml).
The table explains why those obligations cannot be attributed to DRS-1 through DRS-37; it is not a proposal to add unreviewed behaviour.

| Source | Narrative behaviour | Coverage finding |
|---|---|---|
| Chapter 4, introduction | Operate as a multi-tenant platform in which users create and manage registry databases. | DRS-2 requires multiple databases in one system instance and DRS-6 defines access controls, but no DRS requirement establishes tenant boundaries or tenant isolation for the platform as a whole. |
| Chapter 4, Registry lifecycle management | Deprecate registry versions and provide backward-compatibility guidance when a schema changes. | DRS-1 has Draft, Published, and Archived states. DRS-4 requires versioning, breaking-change detection, and warnings, but does not define a Deprecated state or require compatibility guidance. |
| Chapter 4, Registry lifecycle management | Configure deduplication and general data-quality controls. | DRS-3 and DRS-17 contain field validation options, including uniqueness, minimum, and maximum. No DRS requirement states the broader deduplication or data-quality-control behaviour. |
| Chapter 4, Data management | Soft-delete and archive records. | DRS-5 lists an archive-data API and DRS-22 permits deletion, but no DRS requirement defines soft-deletion or archival semantics. |
| Chapter 4, Data management | Apply policy-based redaction as well as masking to sensitive attributes. | DRS-5 mentions optional field-level masking, and DRS-6 covers minimisation and conditional restrictions. No DRS requirement states a redaction operation or its policy semantics. |
| Chapter 4, Interoperability | Automatically generate GraphQL services for each registry. | DRS-5 and DRS-31 require generated API services and DRS-34 requires an OpenAPI service list. None requires GraphQL. |
| Chapter 4, Interoperability | Integrate external systems through the Information Mediator Building Block. | DRS-15 assigns protection of data in transit to the Information Mediator and DRS-19 supports external API exchange. Neither requires Digital Registries integrations to pass through the Information Mediator. Not carried as a separate required statement: the mediation itself is outside the system under test ([scope](../introduction/scope.md#not-covered)). The Digital Registries side is bound where the source states it, in mediated external event subscriptions and the workflow preconditions in [Operate Registry Services](../requirements/operate-registry-services.md) and encryption in transit in [Audit and Personal Data Protection](../requirements/audit-and-personal-data.md). Whether item 13 requires every external integration to pass through the Information Mediator is recorded as a source ambiguity. |
| Chapter 4, Interoperability and Applicant Functions | Emit create, update, and delete domain events through Pub/Sub, with mediated external subscriptions and policy-controlled direct subscriptions inside a trust boundary. | DRS-5 names a subscription API and DRS-19 names webhook triggers. Neither defines the event set, Pub/Sub behaviour, mediation rule, trust-boundary exception, tenant isolation, or subscription audit obligation. |
| Chapter 4, Monitoring and analytics | Report registry usage, performance and data quality, and generate dashboards and administrative reports. | DRS-12 covers API use and search statistics, and is optional. DRS-26 requires registry reports and offers custom dashboards as an option, while chapter 4 lists dashboards among core functions. Neither requires performance or data-quality measurements. Usage, performance and data-quality statistics are bound in [Operate Registry Services](../requirements/operate-registry-services.md). Dashboards are not carried as a separate required statement; they keep the DRS-26 option level, and the level conflict is recorded as a source ambiguity. |
| Chapter 7, Resource Model | Enforce the model's Database-to-Data, Data-to-Audit-Log, Database-to-Schema, and Schema-to-Data relationships and cardinalities. | Individual DRS requirements cover related features, but none binds the complete resource model or its cardinalities as shown. |
| Chapter 7, Minimum Required Data | Every implementation always contains the complete minimum field set, including Schema ID and Registry number, with the listed types. | DRS-1, DRS-2, DRS-3, DRS-7, DRS-8, and DRS-21 cover parts of the set. They do not require the table as one minimum structure, and do not state every listed field and type. |
| Chapter 8, API embeds | Provide each exact method and path listed in the API chapter. | DRS-5, DRS-31, DRS-33, DRS-34, and DRS-35 require API capabilities, but the DRS statements do not bind the exact method-and-path set. The active requirement files and `resources/api.yml` must establish any normative operation binding. |
| Chapter 8, endpoint convention | Form endpoints as `/{information type}/{registry acronym or code}/{version}/{API method as a name}`. | No DRS requirement states this naming convention. The two examples and the embedded contracts also use different prefixes, as recorded below. |
| Chapter 8, API format | Use REST, describe APIs using OpenAPI 3 and YAML, and use JSON request and response bodies. | DRS-34 requires an OpenAPI service list, but the DRS statements do not fully bind the REST style, OpenAPI version, description serialization, or JSON wire format. |
| Chapter 9, User Story 1 | Require administrator authentication, a web interface, internet access, and electricity as preconditions. | DRS-6 requires authorisation and several DRS statements require a web interface. Authentication is not stated as a DRS obligation. Internet access and electricity remain documented workflow prerequisites outside the system under test, not software-conformance requirements. |
| Chapter 9, User Story 2 | Store record changes in a Change Log database. | DRS-7 and DRS-21 require change logs, but do not require a dedicated Change Log database. |
| Chapter 9, User Story 3 | Let developers create, read, modify, and delete registry schemas through APIs, including deletion of all data with a schema. | DRS-28 requires creation, DRS-30 publication, and DRS-32 reading. DRS-31 concerns API-service configuration, not schema update and deletion, so the full schema CRUD workflow is not bound. |
| Chapter 9, User Stories 3 and 4 | Require API clients to connect through the Information Mediator and authenticate applicants through the client system or Security Building Block. | DRS-6 establishes authorisation and DRS-15 discusses encryption in transit. No DRS requirement binds these workflow-specific mediation and authentication preconditions. |
| Chapter 9, User Story 3 | Permit unauthorised schema CRUD when anonymous editing is enabled for a database in the GovStack Sandbox. | DRS-6 requires an Anonymous role to exist but does not authorise anonymous schema administration or define this sandbox exception. |
| Chapter 9, User Story 4 | Store all processing events in a dedicated audit registry. | DRS-7 requires logging but does not require a dedicated audit registry. |
| Chapter 9, User Story 4 | Let all authenticated users read registry data and let unauthenticated users perform CRUD where anonymous processing is enabled. | DRS-6 requires service-, record-, and field-level authorisation, and DRS-33 says the Building Block authorises clients and users. The migrated supplementary requirements retain the anonymous exception only for databases explicitly allowing it. They retain the authenticated-read statement as a documented source conflict for later substantive review, not as an additional access grant. |

## Source ambiguities and unresolved links

- The source landing page identifies the publication as **Version 3.0-alpha; June 2026**. The version table and release notes use **v3.0.0-alpha**. No source page adds another alpha-release suffix.
- The landing page lists Leonora Smart-Abbey and Jeremi Joslin among the 3.0-alpha authors, but the version-history row for 3.0.0-alpha does not. [`authors.yml`](../authors.yml) follows the landing page.
- The release notes list David Higgins and Ali González-García as v3.0.0-alpha authors (spec/1-version-history/release-notes.md:11), while the landing page and version history list them as editors. [`authors.yml`](../authors.yml) follows the landing page.
- The version history dates version 1.0 to May 2023, while the release notes date it to August 2022 and say its first publication date is `TBC`.
- The version history dates version 2.0 to November 2023, while the release notes date version 2.0.0 to December 2023.
- Chapter 7 refers to chapters 7.3.1 and 7.3.2 for schema examples, but neither section exists in the source tree.
- Chapter 7 lists `file` as a permitted field type, but its minimum-data row for Field value lists datetime, date, boolean, text, and number without a file value type.
- Chapter 8's endpoint examples include `/api/data/cr/1.0/create` and `/api/v1/database/modify`. Its stated convention omits the `/api` prefix, and the embedded paths begin with `/data` or `/database` rather than `/api`.
- The Data API source contract declares `POST /data/{registryName}/{versionNumber}/create`, but chapter 8 contains no OpenAPI embed for that operation.
- The chapter 8 Database API embed uses `spec/.gitbook/assets/GovStack_Digital_registries_BB_Database_API_template-1.3.0.yaml`. The root `api/` directory contains a different file with the same name. Their paths and methods match, but their schema references differ. The root file refers to `DatabaseInfo` and `DatabasesSchema` while defining `databaseInfo` and `databasesSchema`; the embedded asset uses matching lower-case references. The migrated page therefore links the exact byte-preserved embedded asset, and the authoring projection copies that embedded asset without synthesising schema or path repairs.
- The decision log contains a relative link to `../registration/`, but no such target exists in this repository. The migrated historical log preserves the words "another document" as plain text rather than redirecting them to an invented destination.
- The decision log says data sharing was added as DRS-33. In the June 2026 functional-requirements chapter, sharing is DRS-27 and DRS-33 concerns client-system CRUD.
- Chapter 4's administrative function list skips item 7 and uses item 12 twice. The migrated page preserves the source numbering.
- Chapter 9 repeats the first six postconditions of User Story 1 as items 7 through 12.
- User Story 1 says an administrator can configure and launch a registry database "instantly", but the source defines no measurable time threshold.
- Chapter 9's Applicant example names both a health-care worker and a mother without clearly assigning their respective roles.
- The Other Resources page links to Atlassian pages for the decision log, future considerations, out-of-scope assumptions, and schema examples. Those external links are preserved unchanged; this migration did not establish whether access is public or whether the external pages match the repository copies.
