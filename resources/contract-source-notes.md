# API Source Selection and Authoring Projection

Upstream chapter 8 embeds the Data API JSON and Database API YAML from `spec/.gitbook/assets/`. Those exact files are the source of this authoring view. Their bytes are copied to [data-api.json](upstream-api/data-api.json) and [database-api.yaml](upstream-api/database-api.yaml). All original alternative files remain unchanged in the repository.

[resources/api.yml](api.yml) is generated by `tools/build_api_projection.py`. It copies complete Operation Objects and Path Items, not invalid Operation Object `$ref` overlays. Existing operation IDs, methods, paths, request and response constraints, security requirements and server context are preserved. Local schema references are rebased to their exact original contract copies. Security component names are namespaced in this combined authoring document (`data__apiKey` and `database__apiKey`) so one source cannot silently overwrite the other; their source definitions are referenced unchanged.

The projection contains 15 original operations. The four Database operations had no identifiers, so this authoring document supplies aliases only:

| Original operation | Authoring alias |
| --- | --- |
| GET `/database/{id}` | `getDatabase` |
| DELETE `/database/{id}` | `deleteDatabase` |
| POST `/database/modify` | `modifyDatabase` |
| GET `/databases` | `listDatabases` |

`modifyDatabase` retains the original description, create or modify a schema. `listDatabases` lists databases; it is not misrepresented as the missing API-service catalog. These aliases do not add an endpoint or alter its behaviour. The original templates are still byte-identical and still omit these IDs.

## Divergent source copies

The root Data JSON and embedded Data JSON match. Data YAML differs from JSON in operation coverage, parameter casing, personal-data usage path casing and an operation identifier. The migration does not merge those differences into an invented API.

The root Database JSON and YAML contain unresolved schema references with different casing. The embedded Database YAML resolves those names but also differs in a schema reference. The projection uses the document explicitly embedded by chapter 8, without synthesizing schema repairs from the alternatives. The repository `api/readme.txt` prefers JSON definitions while chapter 8 embeds both formats; that source inconsistency is retained.

[Paired validation results](contract-validation.json) records the same validator against the pinned and migrated original bytes. Both root Database alternatives retain their pre-existing `PointerToNowhere` failures. The two selected embedded contracts and the generated authoring projection validate. A passing projection does not mean the divergent original alternatives were fixed.

Reproduce with `uv run python tools/build_api_projection.py --check`, `uv run python tools/report_contracts.py --check`, and `uv run openapi-spec-validator resources/api.yml`.

## Unspecified contracts

The source requires more behaviour than its templates standardize, including publishing through an API, API configuration, GraphQL, event subscription, rights management, custom views and statistics APIs. Those gaps remain listed in the [source findings](source-findings.md), with empty operation IDs where no operation exists. No guessed endpoint is presented as upstream-standardized behaviour.
