# Conformance and Optionality

This authoring migration does not ratify or publish a specification. New-format requirement IDs remain empty and lifecycle is DRAFT; source identifiers DRS-1 through DRS-37 remain exact lookup keys in the migration ledger. No accepted requirement identifiers are invented.

Source REQUIRED behaviour remains REQUIRED in core. The four complete optional functionalities, database views (DRS-9), service usage statistics (DRS-12), schema templates (DRS-20), and statistical-query APIs (DRS-36), are independent extensions with no introduced dependency. Requirements inside a claimed extension are REQUIRED; an unclaimed extension does not become a failed core requirement. The source itself crosses that boundary in places, such as the required view-based custom API of DRS-5 and the views inside a DRS-20 template; those clauses keep their source levels and are listed in the [overview](../introduction/overview.md#core-and-extensions).

Chapter 6 says its requirements are the capabilities that any implementation must support (spec/6-functional-requirements.md:9). Most DRS blocks carry a REQUIRED or OPTIONAL marker on the heading or a lead item; DRS-2 places it on an example (spec/6-functional-requirements.md:39), DRS-10 on its export line, which also notes XLS as optional (:165), DRS-15 on its second bullet (:195), and DRS-11 marks its JSON/YAML and XLS sentences separately (:169). A bullet without its own marker takes the block level, including bullets phrased with "has the option to" or "should"; where the source pairs "should" with REQUIRED (DRS-2, DRS-26, chapter 8) the tension is recorded as a source ambiguity. A bullet the source itself marks optional is mapped as described below.

Nested optional improvements and optional personal-data field marking remain nonblocking RECOMMENDED requirements within their functionality. Their documentation retains the original optional qualification. This mapping uses the framework's nonblocking recommendation mechanism instead of turning each optional field or file variant into a new all-or-nothing extension. It does not upgrade an optional behaviour into a mandatory core obligation.

The source contains overlaps and contradictions between required and optional clauses. They remain visible in the [source findings](source-findings.md); the format migration does not settle them. Conditions in the documentation retain their original scope, including legal applicability, explicitly enabled anonymous access and the sandbox context. They do not grant additional production access.

SERVICE_API requirements name a real operation in the authoring projection where the upstream templates supply one. Missing bindings remain empty and are exhaustively listed as known source gaps. Preservation validation requires an exact explained ledger entry for each such gap, and rejects invented identifiers. That permits an honest draft migration; it does not claim strict compiler completeness or interoperability for the missing contracts.

Chapter 8 calls its listed APIs "a minimal set of functionality that should be provided by any implementation" and says the Building Block "is expected to host" them (spec/8-service-apis.md:9, :31). The migration reads that minimal set as REQUIRED and gives each listed operation its own API-TEMPLATE statement; the "should" wording is recorded as a source ambiguity. The same operation can also bind a workflow statement, such as the chapter 9 schema-administration statements for the four Database operations, or a DRS statement. Those overlapping bindings are intentional: each statement keeps its own source clause, so one operation result can contribute evidence to several statements.

The current major version's coordinators, authors and editors are carried from the original landing page into [`authors.yml`](../authors.yml), which by framework convention lists only this version's authors. That file has no affiliation field, so the landing page's "(Aam Digital)" note and its "First version by" credits with affiliations are not carried into it; they remain in the frozen `spec/README.md`, and the [version history](version-history.md) keeps the earlier authors' names. Registration URNs remain unassigned where not verified. Formal publication registration and resolution of inherited source gaps are separate from this migration.
